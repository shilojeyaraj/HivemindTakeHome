# CLAUDE.md: Hivemind Winter '27 Co-op Take-Home

## Project Summary

Build a working web interface that lets a person supervise a persistent AI agent that worked for them overnight. The agent books a multi-city trip while the user sleeps. The interface shows what happened, separates FYI updates from decisions that need the user, and lets the user approve, deny, or redirect those decisions.

The evaluators care most about **judgment and taste in user-centric design**, not code quality. Every design choice should be defensible in the write-up.

## Context (from the assessment)

Persistent agents now remember context across days, act across apps, and proactively message the user. Examples: Instinct, xAI's Grok Bot, Meta's Muse. Models are reliable enough to be left alone overnight.

Core question: **When an agent works for 8 hours while you sleep, what should be on your screen when you wake up?** What does the ideal interface for human-agent interaction look like?

## The Scenario

Before bed, the user tells the agent:

> "Book my reading week trip - going from Toronto to New York to Boston and back, leaving October 10, home by October 18, under $1,500 total, find window seats where you can."

- The agent has the user's card on file.
- The user is asleep for 8 hours.
- Overnight the agent hits tradeoffs such as:
  - 6 AM departure vs. noon departure at +$140
  - Connection vs. direct flight at +$180
  - Cheap hotel that is 40 minutes from the city's best attraction
  - A fare that expires in 20 minutes while the user is asleep

## Agent in Use

- **Primary agent: Instinct** (app.instinct.com). The user has an account and is actively using it.
- Muse and Grok Bot are stretch-goal candidates only if time allows.
- Event model `agent` field should default to `"instinct"`.

## What to Build

1. **Set up at least one real persistent agent**: Instinct (invite: https://app.instinct.com/invite?t=waterloo-takehome), Meta's Muse, or Grok Bot.
2. **Converse with the agent** so it learns personalized context (preferences, budget habits, seat preferences, etc.).
3. **Run the trip scenario overnight** on the agent(s).
4. **Build one working demo interface** using the **actual data generated by the agent(s)**. No fabricated data.
5. The interface must show **both moment types**:
   - **Context-only updates**: nothing needed from the user (e.g. "Shortlisted 3 Boston hotels").
   - **Action-required decisions**: approve / deny / redirect, with **working steering** that actually affects the agent.
6. **Stretch goal (strongly encouraged):** connect **more than one agent**. The interface should interview every agent, fact-check them against each other, and question each one until it produces the most reliable output for the user's decision or daily update.

## Key Constraints

- **Design for latency.** Agents are slow. The UI must handle waiting, partial results, and in-progress states gracefully.
- **The agent will do dumb things.** Mistakes must be visible and recoverable, never hidden.

## Questions the Write-Up Must Answer

1. **Autonomy boundary:** What is the agent allowed to decide on its own overnight, and what must wait for the user to wake up? Where is the boundary and why?
2. **The 3 AM layover case:** It is 3 AM and the only routing left under budget has a 6-hour layover. What happens, and how does the interface show that decision in the morning?
3. **Trust over time:** Trip 1 vs. trip 10. How does the agent earn more autonomy over time?

Underlying theme: **trust, delegation, and what a person needs to feel in control of something that acts without them.**

## Build Plan

### Step 1: Agent setup and data collection (do first, needs an overnight run)
- Sign up for the agent(s) and seed personal context.
- **Investigate integration surface for each agent:** API, webhooks, exports, or chat-only. This determines how real the steering can be.
- Ask the agent to report in a structured format where possible (decisions with options, costs, deadlines, reasoning).
- Kick off the scenario before sleeping. Save all raw logs/transcripts.

### Step 2: Normalize agent output into an event model
Parse raw agent output into a common schema so multiple agents can be compared. Suggested shape:

```ts
type AgentEvent = {
  id: string;
  agent: "instinct" | "muse" | "grok";
  timestamp: string;
  kind: "update" | "decision" | "error" | "auto_action";
  title: string;
  summary: string;
  reasoning?: string;
  sourceEvidence?: string;          // raw excerpt from agent output
  options?: DecisionOption[];       // for decisions
  deadline?: string;                // e.g. fare expiry
  autoResolved?: {                  // what the agent did on its own
    choice: string;
    reversible: boolean;
    undoBy?: string;
  };
  confidence?: "high" | "medium" | "low";
  crossCheck?: {                    // multi-agent fact-check result
    agreesWith: string[];
    conflictsWith: { agent: string; detail: string }[];
  };
};

type DecisionOption = {
  label: string;
  costDelta?: number;
  tradeoff: string;
  recommended?: boolean;
};
```

### Step 3: Build the morning interface
Suggested views:
- **Morning brief:** one-screen summary. Trip status, total spend vs. $1,500 budget, number of decisions waiting.
- **Decision queue:** action-required items first, sorted by urgency (expiring fares first). Approve / deny / redirect with free-text redirect.
- **Overnight timeline:** chronological log of everything the agent did, including auto-actions, with the ability to expand reasoning and raw evidence.
- **Mistakes and reversals:** errors and questionable auto-actions surfaced explicitly, each with an undo or fix path.
- **Multi-agent comparison (stretch):** side-by-side results, conflicts flagged, and a resolved recommendation.

### Step 4: Steering
- Best case: actions call the agent's API directly.
- Fallback: the interface records the decision and relays it back to the agent via its chat channel. Document this as a constraint and design choice.

### Step 5: Write-up and Loom
- Record the Loom last, walking through the morning experience as the user would.
- Keep the write-up concise and opinionated.

## Design Principles to Explore (starting points, refine during the build)

- Reversible and low-cost actions within explicit user rules can be autonomous; irreversible or rule-breaking actions wait.
- Holds and refundable bookings can buy time when a decision is urgent but the user is asleep.
- Every auto-decision should show what was chosen, what was rejected, why, and how to undo it.
- Autonomy should expand based on the user's track record of approvals, not be granted all at once.
- Latency should be visible as progress, never as a blank or frozen screen.
